# Phase 18.5 — Identity reference storage, biometric-reference schema, and optional cache architecture

Use `prompts/00-ai-agent-rules.md` first.

## Objective

Implement the storage and cache architecture agreed after Phase 18 integration-contract review.

This milestone closes the gap between the functional identity-reference domain and the revised face-biometric-service integration architecture. It defines durable storage for versioned identity photos and multiple model-aware biometric embeddings, while making Redis completely optional and removing Caffeine as a required runtime dependency.

The implementation must preserve the service's ability to run in a minimal **Oracle-only mode**:

- Oracle enabled;
- Redis disabled;
- Caffeine absent/disabled;
- no hidden cache dependency during startup or normal operation.

The same application must also support an optional Redis mode through configuration, without changing business code.

## Important architectural decisions

### 1. Service ownership

`identity-reference-service` owns:

- identity/reference records;
- provider acquisition and refresh;
- identity/photo history;
- biometric-reference lifecycle;
- persistence of encrypted photos;
- persistence of encrypted biometric embeddings;
- model-aware reference lookup;
- Redis hot-cache projection when Redis is enabled.

`face-biometric-service` owns:

- face detection;
- liveness;
- alignment;
- embedding generation;
- biometric verification.

Do **not** make face-biometric-service directly access this service's Oracle database or Redis.

Normal ready-reference lookup is synchronous.

If a required reference is missing, expired, or not prepared for the requested model, the integration contract may return a pending/inconclusive state and the acquisition/preparation workflow can proceed asynchronously. Do not turn "reference unavailable" into a biometric NO_MATCH.

### 2. Multiple photos per identity

An identity reference may have multiple photos over time.

Create a dedicated versioned photo persistence model/table, logically:

`IDENTITY_REFERENCE 1 -> N IDENTITY_PHOTO`

Each photo must preserve provenance and version information.

The photo model should support at least:

- id;
- identity reference id;
- photo version;
- source/provider information;
- provider photo id where available;
- captured/effective/acquired timestamps;
- content type;
- content length;
- content hash;
- encrypted photo data;
- encryption key id/version/algorithm metadata;
- lifecycle/status;
- current/preferred marker where useful;
- created/updated timestamps.

Do not overwrite historical photos merely because a newer photo arrives.

The preferred/current photo must be selected according to the provider/domain policy and photo effective/capture/version information. Do not blindly use acquisition time as the definition of "newest".

Preserve enough provenance to answer:

> Which exact source photo produced this biometric embedding?

### 3. Multiple embeddings per identity/reference

An identity reference may have multiple embeddings.

Create a dedicated model-aware biometric embedding persistence model/table:

`IDENTITY_REFERENCE 1 -> N BIOMETRIC_EMBEDDING`

An embedding must be associated with the exact source photo:

`IDENTITY_REFERENCE -> IDENTITY_PHOTO -> BIOMETRIC_EMBEDDING`

Store, at minimum:

- id;
- identity reference id;
- photo id;
- model id;
- model version;
- dimension;
- metric;
- normalized flag;
- embedding/generation version;
- encrypted vector data;
- encryption key id/version/algorithm metadata;
- generated-at timestamp;
- generator service/version;
- lifecycle/status;
- created/updated timestamps.

The canonical compatibility identity of an embedding is the complete model metadata tuple, not the vector dimension alone.

Never infer that two embeddings are compatible merely because both have dimension 512.

The design must support examples such as:

- ArcFace / w600k-r50 / 512 / cosine / normalized;
- another installed model with the same dimension but different model identity/version;
- multiple embeddings generated from different photo versions.

A useful logical uniqueness rule is:

`(PHOTO_ID, MODEL_ID, MODEL_VERSION, EMBEDDING_VERSION)`

or an equivalent constraint justified by the actual generation lifecycle.

Do not store vectors as JSON strings. Prefer an encrypted BLOB with a documented binary representation, such as float32 values, so the schema remains independent of a particular Oracle vector feature.

### 4. Proposed core Oracle model

Keep `IDENTITY_REFERENCE` as the parent/master record.

The core durable model should contain:

1. `IDENTITY_REFERENCE`
2. `IDENTITY_PHOTO`
3. `BIOMETRIC_EMBEDDING`

A separate provider/raw-payload table may remain where the existing architecture requires it; do not duplicate provider payload storage unnecessarily.

The existing identity-reference table should retain its lifecycle, refresh, provider, and lookup concerns.

Evaluate and evolve the current schema rather than blindly replacing it.

The final migration must be backward-compatible with existing data and must not drop production data.

### 5. Sensitive identity data

Do not treat every field identically.

Use a security classification based on actual application use:

| Data | Intended protection |
|---|---|
| Internal random reference UUID | Plain/random |
| National-ID lookup value | Keyed HMAC/lookup token where equality lookup is required |
| Recoverable national ID | Authenticated encryption when the application must recover it |
| Names | Encryption where required |
| Birth date | Encryption where required |
| Father name | Encryption where required |
| Other sensitive personal attributes | Encrypt according to final classification |
| Photo | Encrypted BLOB |
| Photo content hash | Cryptographic hash |
| Embedding vector | Encrypted BLOB |
| Model metadata | Non-secret metadata |
| Status/timestamps | Non-secret operational metadata |
| Encryption key identifier/version | Metadata only; never the key itself |

Do not use plain unsalted SHA-256 as a national-ID lookup mechanism.

Do not put encryption keys in Oracle, Redis, source code, or ordinary application properties.

Use the project's approved secret-management mechanism (Vault or the final selected equivalent) for actual keys.

This milestone must establish the schema and service interfaces so that encryption is a first-class storage concern. Coordinate with the existing Phase 21 data-protection milestone; do not claim a ciphertext column is actually secure merely because it is named `*_CIPHERTEXT` or `*_ENC`.

If encryption infrastructure is already implemented, use it. Otherwise introduce a clean storage/crypto abstraction and leave final cryptographic implementation to the designated data-protection milestone rather than inventing a second incompatible crypto system.

### 6. Photo storage

For this milestone, store photos in Oracle for simplicity.

Use an Oracle BLOB for encrypted photo data.

Do not hard-wire the domain model to Oracle BLOB forever.

Introduce a storage abstraction at the service boundary so a later decision can move photo storage to:

- filesystem;
- MongoDB;
- object storage;
- Oracle;
- another approved store.

Changing photo storage later should require changing the storage adapter/implementation, not redesigning identity/photo/embedding domain relationships.

### 7. Redis must be optional

Redis must become a configurable optimization, not a required persistence layer.

Provide an explicit property such as:

`identity.cache.redis.enabled=true|false`

Use the project's existing property naming conventions if a better established name exists.

Required behavior:

#### Redis enabled

- Oracle remains the source of truth.
- Redis provides the optional hot/cache projection.
- Cache misses fall back to Oracle.
- Cache failures must not corrupt the durable record.
- Sensitive cached data must follow the project's final data-protection policy.
- Do not cache all historical photos/embeddings for millions of identities unnecessarily.
- Prefer current/hot projections.

Conceptual keys may include:

- `identity-ref:{referenceId}`
- `identity-ref:{referenceId}:photo:current`
- `identity-ref:{referenceId}:embedding:{modelId}:{modelVersion}`

Use a stable, versioned key namespace.

#### Redis disabled

- The application must start successfully without a Redis connection.
- No Redis connection bean/client must be required by unrelated services.
- No Redis health check should make the application unhealthy when Redis is disabled.
- Normal lookup and persistence must work directly against Oracle.
- Cache-aside decorators/adapters must become no-ops or be conditionally absent.
- Redis-specific repositories/configuration must be conditional.
- Tests must prove startup and core operations with Redis disabled.

Do not merely ignore Redis connection errors after startup. Redis must genuinely be optional at configuration/bean-creation level.

### 8. No Caffeine requirement

Caffeine is no longer a required cache layer.

Do not design a mandatory:

`Caffeine L1 -> Redis L2 -> Oracle`

architecture.

The preferred architecture is now:

`Oracle -> optional Redis hot cache`

with:

`Oracle-only mode`

as a fully supported deployment mode.

If the current project still contains Caffeine configuration, beans, dependencies, or service wiring, inspect all usages and remove the runtime requirement.

Do not introduce a replacement in-memory cache merely because Caffeine is removed.

If a tiny local optimization is later desired, it must be a separately configurable feature and must never become required for correctness.

### 9. Cache data model

Do not make Redis the authoritative home for:

- historical photos;
- historical embeddings;
- provider history;
- durable lifecycle state.

Oracle remains the durable source of truth.

Redis should contain only the current/hot representation required for performance.

Cache invalidation/update must follow photo and embedding version changes.

When a newer photo becomes current:

1. update Oracle;
2. update or invalidate the Redis current-photo projection if Redis is enabled;
3. ensure old cached embeddings cannot be accidentally returned as the current model reference unless an explicit fallback policy permits it.

When a new embedding is generated:

1. persist it durably;
2. publish/update the compatible Redis projection if enabled;
3. make model metadata part of the lookup key/selection.

### 10. Face-biometric integration implications

The Phase 18 contract must remain model-aware.

A lookup from face-biometric-service should identify the requested model completely, for example:

- modelId;
- modelVersion;
- dimension;
- metric;
- normalized.

The identity-reference-service returns the exact compatible stored embedding and its source-photo metadata.

If the current photo is newer but its requested model embedding is still pending, do not silently substitute an older embedding unless an explicit fallback policy exists and is part of the contract.

If no compatible embedding exists, return a clear pending/inconclusive/reference-unavailable state rather than NO_MATCH.

For long-running acquisition/preparation, use a correlation/verification/request ID. Do not use only the customer/reference ID as the correlation key because concurrent verification requests for the same customer are possible.

Synchronous REST is the normal ready-reference lookup path.

Kafka/event-driven processing should be used for long-running acquisition, preparation, embedding generation, and completion events—not as a replacement for every normal reference lookup.

The identity service should request explicit model spaces that are actually required. Do not blindly generate every installed model unless policy explicitly requires it.

### 11. Flyway and JPA requirements

Inspect all existing Flyway migrations and current JPA entities before editing.

Implement the schema incrementally.

Required database work should include:

- `IDENTITY_PHOTO` table;
- `BIOMETRIC_EMBEDDING` table;
- foreign keys;
- uniqueness constraints;
- lookup indexes;
- current/preferred-photo support;
- model-aware embedding indexes;
- versioning/provenance fields;
- LOB/BLOB definitions appropriate for Oracle;
- safe migration of any existing compatible data.

Do not drop existing identity-reference data.

Do not create redundant columns merely to mirror DTOs.

Keep database constraints aligned with actual service invariants.

### 12. Application configuration

Separate configuration concerns clearly.

At minimum support:

- Oracle required;
- Redis optional;
- Caffeine not required.

Document the expected combinations.

Example conceptual modes:

`oracle-only`
- Oracle: enabled
- Redis: disabled
- Caffeine: absent/disabled

`oracle-plus-redis`
- Oracle: enabled
- Redis: enabled
- Caffeine: absent/disabled

The application must not require Redis simply because Redis libraries are on the classpath.

Prefer conditional configuration such as `@ConditionalOnProperty` or equivalent Spring configuration patterns.

### 13. Tests

Add focused automated tests for:

#### Persistence

- multiple photos for one identity;
- photo version ordering;
- current/preferred photo selection;
- multiple embeddings per photo/reference;
- model metadata matching;
- same dimension but different model IDs are not treated as compatible;
- embedding-to-photo provenance;
- duplicate/content-hash handling where applicable.

#### Redis disabled

- application context starts without Redis;
- no Redis connection is attempted by core paths;
- Oracle lookup works;
- Oracle persistence works;
- cache layer is absent/no-op;
- Redis health/metrics do not fail the application.

#### Redis enabled

- cache-aside lookup;
- cache miss -> Oracle;
- cache update/invalidation;
- Redis failure -> durable Oracle behavior remains correct;
- current-photo and model-aware embedding keys are correct.

#### Security

- no secrets or sensitive identity values in logs;
- encryption metadata is preserved;
- crypto abstraction is invoked where required;
- no raw biometric vector is accidentally serialized into ordinary API/log output.

#### Integration contract

- exact model compatibility tuple;
- ready reference;
- reference unavailable/pending;
- newer photo with missing embedding;
- concurrent requests use distinct correlation IDs.

Run the complete Maven verification suite and relevant integration tests.

## Non-goals

Do not:

- implement a national-agency integration not already defined;
- make face-biometric-service access Oracle directly;
- replace Oracle as the durable source of truth;
- introduce a mandatory in-memory cache;
- make Caffeine a hidden dependency;
- generate embeddings inside identity-reference-service using face-recognition models;
- infer model compatibility from dimension;
- overwrite historical photos;
- silently treat missing references as NO_MATCH;
- redesign the entire face-biometric-service;
- duplicate the full Phase 21 cryptographic implementation if it is not yet ready.

## Acceptance criteria

Phase 18.5 is complete only when:

1. The Oracle schema supports multiple versioned photos per identity.
2. The Oracle schema supports multiple model-aware embeddings and exact photo provenance.
3. The schema can store encrypted photo and embedding payloads without exposing keys.
4. Photo storage is behind an abstraction so a future storage backend can replace Oracle BLOB.
5. Redis can be enabled/disabled entirely through configuration.
6. The service starts and operates correctly with Oracle only.
7. No Caffeine cache is required for startup, correctness, or normal operation.
8. Redis-enabled behavior remains cache-aside and Oracle remains authoritative.
9. Face-biometric integration remains model-aware and does not directly access identity-service persistence.
10. Missing/stale/unprepared references have explicit pending/inconclusive semantics.
11. Automated tests cover Oracle-only and Redis-enabled modes.
12. Existing application properties containing real infrastructure endpoints/secrets are not overwritten with localhost/default values.
13. Maven verification passes.
14. Documentation/report is updated.
15. The milestone is committed with a focused commit message.
